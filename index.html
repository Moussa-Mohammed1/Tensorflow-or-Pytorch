Objectif et plan

1. Origines et philosophie

TensorFlow / Keras

  • Google Brain, 2015
  • Pensé pour la production à grande échelle : graphes optimisés, calcul distribué
  • Keras : API de haut niveau, intégrée depuis TF 2.0
  • Keras 3 : multi-backend (TensorFlow, JAX, PyTorch)

PyTorch

  • Facebook AI Research, 2016 (héritier de Torch)
  • Philosophie « Pythonic » : un modèle est une classe Python
  • Exécution ligne par ligne, débogage avec print et pdb
  • Standard de la recherche académique

1. Graphe de calcul et style de programmation

  • TensorFlow 1.x : graphe statique construit avant exécution, optimisé mais difficile à déboguer.
  • TensorFlow 2 : eager execution par défaut ; compilation en graphe avec @tf.function.
  • PyTorch : graphe dynamique (define-by-run) recréé à chaque passe avant ; boucles et conditions Python autorisées. torch.compile (PyTorch 2) pour accélérer.
  • Keras : style déclaratif — compile() puis fit().
  • PyTorch : style impératif — boucle d’entraînement écrite par l’utilisateur.
Keras : simplicité et rapidité. PyTorch : contrôle total et flexibilité.

1. Même modèle, deux écritures

# Keras
import tensorflow as tf
model = tf.keras.Sequential([
  tf.keras.layers.Dense(64,
      activation="relu",
      input_shape=(20,)),
  tf.keras.layers.Dense(1,
      activation="sigmoid")
])

Déclaratif : on empile des couches.

# PyTorch
import torch, torch.nn as nn
class Net(nn.Module):
  def __init__(self):
    super().__init__()
    self.fc1 = nn.Linear(20, 64)
    self.fc2 = nn.Linear(64, 1)
  def forward(self, x):
    x = torch.relu(self.fc1(x))
    return torch.sigmoid(self.fc2(x))
model = Net()

Impératif : on écrit le forward.

2. Les tenseurs

Tableau multidimensionnel défini par sa forme, son type (dtype) et son périphérique (CPU, GPU, TPU). Rang 0 : scalaire ; 1 : vecteur ; 2 : matrice ; 4 : lot d’images couleur.

  • Mutabilité : tf.Tensor immuable (paramètres via tf.Variable) ; torch.Tensor modifiable sur place.
  • Dérivation automatique : tf.GradientTape contre requires_grad=True et autograd.
  • Périphérique : placement automatique sur GPU (TF) contre .to("cuda") explicite (PyTorch).
a = tf.constant([[1., 2.], [3., 4.]])     # TensorFlow
b = torch.tensor([[1., 2.], [3., 4.]])    # PyTorch
a_np, b_np = a.numpy(), b.numpy()         # conversion NumPy
b = b.to("cuda" if torch.cuda.is_available() else "cpu")

2. Pipelines de données

TensorFlow : tf.data

Pipeline déclaratif : map, shuffle, batch, cache, prefetch. Couches de prétraitement Keras intégrables au modèle.

ds = (tf.data.Dataset
  .from_tensor_slices((X, y))
  .shuffle(1000)
  .batch(32)
  .prefetch(tf.data.AUTOTUNE))

PyTorch : Dataset + DataLoader

__len__ et __getitem__ définissent le jeu ; le DataLoader gère lots, mélange et chargement parallèle. torchvision.transforms pour l’augmentation.

ds = TensorDataset(
  torch.tensor(X), torch.tensor(y))
loader = DataLoader(ds,
  batch_size=32, shuffle=True,
  num_workers=2)

2. Étapes de préparation des données

  1. Nettoyage et séparation : entraînement, validation, test, sans fuite d’information.
  2. Normalisation / standardisation des entrées pour stabiliser l’apprentissage.
  3. Encodage des variables catégorielles (one-hot, indices, embeddings).
  4. Augmentation (rotations, retournements, bruit) contre le surapprentissage.
  5. Mise en lots et chargement efficace vers le GPU.
Attention : format des images — TensorFlow : channels-last (N, H, L, C) ; PyTorch : channels-first (N, C, H, L). Source fréquente d’erreurs de forme.

3. Principe et fonction de perte

Pour chaque lot : passe avant → perte → rétropropagation (gradients) → mise à jour des poids. Les métriques évaluent le modèle sans intervenir dans l’optimisation.

TâcheKerasPyTorch
RégressionMeanSquaredErrornn.MSELoss
Classification binaireBinaryCrossentropynn.BCELoss / BCEWithLogitsLoss
MulticlasseSparseCategoricalCrossentropynn.CrossEntropyLoss

Note : CrossEntropyLoss attend des logits bruts (sans softmax) et des indices de classes.

3. Optimiseur et métriques

Optimiseur

  • SGD (momentum), RMSprop, Adam, AdamW
  • Taux d’apprentissage : hyperparamètre le plus sensible
  • Schedulers : décroissance exponentielle, cosinus, réduction sur plateau
  • Keras : passé à compile()
  • PyTorch : optim.Adam(model.parameters(), lr=1e-3)

Métriques

  • Classification : accuracy, précision, rappel, F1, AUC
  • Régression : MAE, RMSE
  • Keras : metrics=[…] dans compile()
  • PyTorch : calcul manuel ou bibliothèque TorchMetrics

3. Boucle d’entraînement comparée

# Keras : encapsulé
model.compile(
  optimizer="adam",
  loss="binary_crossentropy",
  metrics=["accuracy"])
model.fit(ds, epochs=10,
  validation_data=val_ds)

Personnalisable par callbacks : EarlyStopping, ModelCheckpoint, TensorBoard.

# PyTorch : explicite
for epoch in range(10):
  model.train()
  for xb, yb in loader:
    optimizer.zero_grad()
    loss = criterion(
      model(xb).squeeze(), yb)
    loss.backward()
    optimizer.step()
  model.eval()
  with torch.no_grad():
    ...  # validation

Contrôle total ; PyTorch Lightning automatise la boucle.

3. Pièges fréquents

  • Oublier optimizer.zero_grad() en PyTorch : les gradients s’accumulent.
  • Oublier model.eval() et torch.no_grad() à l’évaluation : dropout et batch norm restent actifs.
  • Appliquer un softmax avant une perte qui l’inclut déjà (double softmax).
  • Ne pas comparer perte d’entraînement et de validation : le surapprentissage passe inaperçu.
  • Fixer des graines aléatoires pour la reproductibilité des résultats.

4. Sauvegarde et chargement

TensorFlow / Keras

Fichier unique : architecture, poids, configuration, état de l’optimiseur. Format .keras (ancien .h5). SavedModel pour le déploiement.

model.save("modele.keras")
model = tf.keras.models \
  .load_model("modele.keras")
model.export("saved_model_dir")

PyTorch

Pratique recommandée : sauvegarder le state_dict, recréer l’architecture, recharger les poids. Checkpoint complet pour reprendre l’entraînement.

torch.save(model.state_dict(),
           "poids.pth")
model = Net()
model.load_state_dict(torch.load(
  "poids.pth", weights_only=True))
model.eval()

Sécurité : torch.load repose sur pickle ; utiliser weights_only=True ou le format safetensors.

5. Critères de choix

  • Nature du projet : recherche et prototypage → PyTorch ; production, mobile, web → TensorFlow ; apprentissage et projets rapides → Keras.
  • Compétences de l’équipe : expérience, documentation, communauté.
  • Écosystème : Hugging Face très orienté PyTorch ; Keras 3 offre une API unique avec choix du backend.
  • Matériel et performance : CUDA et entraînement distribué dans les deux ; avantage historique de TensorFlow sur TPU. Les écarts dépendent surtout du modèle et du pipeline de données.
  • Déploiement visé : serveur, mobile, navigateur, embarqué.

Conclusion

  • Les deux frameworks ont convergé : exécution immédiate, compilation optionnelle, différentiation automatique, modèles pré-entraînés.
  • Différence principale : simplicité (Keras) contre contrôle explicite (PyTorch).
  • TensorFlow : chaîne de déploiement mature. PyTorch : domination de la recherche.
  • Les concepts communs (tenseurs, perte, optimiseur, métriques, sérialisation) rendent le passage de l’un à l’autre aisé.
Le bon choix : celui qui répond aux contraintes du projet et aux compétences de l’équipe.
